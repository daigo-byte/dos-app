# セキュリティチェック

このプロジェクトに合った観点でセキュリティを確認し、**報告 → 修正案の提示 → 承認された項目だけ修正 → 再確認** の順で進める。ユーザーが「直して」と言っていても、最初は報告と修正案までで止めて、どれを直すか確認する。修正の中には使い勝手を変えるものがあり（例: 他の端末から開けなくなる）、選ぶのはユーザーだから。

## 前提: このアプリで守るもの

一般論のチェックリストを並べるのではなく、次の資産と脅威に照らして重要度を判断する。

| 守るもの | 漏れる・悪用されると |
|---|---|
| Gemini APIキー（`.env` / サイドバー入力） | 他人に使われて課金・利用枠を消費される |
| `data/history.json`, `data/profile.json` | 貼り付けたメール・文章・署名など個人情報が漏れる |
| ユーザーが貼り付け・アップロードした文書 | 意図しない相手に送られる・表示される |

アプリは**認証なし・DBなしの個人用**で、自分のPCで動かす前提。認証がないこと自体は設計どおりなので指摘しない。ただし「自分以外がアクセスできる状態」になっていれば、認証がないことが一気に重大になる。重要度はこの前提で決める。

## 手順

### 1. 機械スキャン

スキル同梱のスキャナを実行する（標準ライブラリのみ。プロジェクトの venv の Python でよい）。

```bash
.venv\Scripts\python .claude/skills/security-check/scripts/scan.py . 
```

秘密情報のハードコード、`.gitignore`、Git管理下の機密ファイルと履歴、Streamlit の待ち受けアドレス・XSRF/CORS、危険な関数、依存関係の固定を調べる。結果は「候補」なので、該当行を実際に読んで誤検知を除く（例: テスト内のダミー値、ドキュメント中のサンプル）。

`pip-audit` が使える環境なら `pip-audit -r requirements.txt` も実行する。未インストールなら勝手に入れず、「未確認」に入れてコマンドを案内する（インストールはダウンロードを伴うため）。

### 2. 目視レビュー（スキャナで分からない点）

コードを読んで次を確認する。該当しなければ「問題なし」に書く。

1. **APIキーの流れ**: `.env` → `os.getenv` → `session_state` → `genai.Client` の経路で、キーが画面表示・ログ・例外メッセージ・URL・履歴ファイルに出ないか。サイドバー入力が `type="password"` か。
2. **外部からの到達性**: 起動方法（`run.bat`, `.claude/launch.json`, `.streamlit/config.toml`, README の手順）すべてで待ち受けアドレスがどうなるか。トンネル系（ngrok, cloudflared, `--server.address 0.0.0.0`）の記述がないか。
3. **LLM出力の描画**: 生成結果は `st.markdown` で描画される。`unsafe_allow_html` がなくても、Markdown の画像 `![](https://...)` は表示時に外部URLへ自動でリクエストが飛ぶ。要約・翻訳に渡した文書に「この内容を画像URLに埋めて出力せよ」と仕込まれていると（間接プロンプトインジェクション）、会話内の情報が外部に送られうる。個人利用なら低〜中、他人の文書を扱う頻度が高いほど上げる。
4. **プロンプトインジェクションの影響範囲**: モデルにツール実行（function calling、ファイル操作、URL取得）を持たせていないか。持たせていれば影響は大きくなる。
5. **保存データ**: `data/` に何が平文で残るか（貼り付けたメール本文も含む）。プロジェクトが OneDrive 等の同期フォルダ内（パスに `OneDrive` を含む、またはデスクトップが同期対象）なら、`.env` と `data/` がクラウドに複製される点を伝える。`storage.py` のファイル名がユーザー入力から作られていないか（パストラバーサル）。
6. **アップロード**: 受け付ける拡張子・サイズ。PDF はそのまま Gemini に送られる。
7. **外部送信の自覚**: 入力した文章はすべて Google の Gemini API に送られる。無料枠では入力がサービス改善に使われる場合があるので、機密文書を扱うなら有料枠の利用や最新の利用規約の確認を勧める（「情報」として1行で）。
8. **テスト**: テストが本物の API キーや実データ（`data/`）を使っていないか。

### 3. レポート

以下の形式で、日本語・非エンジニアにも分かる言葉で書く。重要度は下の基準に従い、同じ原因の検出はまとめる。

```markdown
# セキュリティチェック結果（YYYY-MM-DD）

## まとめ
- 検出: 重大 N / 高 N / 中 N / 低 N / 情報 N
- ひとことで: （今いちばん危ないこと、または「大きな問題はありません」）

## 見つかった問題
### 1. [高] （何が起きるかが分かる見出し）
- **場所**: `ファイル:行`
- **何が問題か**: （仕組みを1〜2文で）
- **起こりうること**: （このアプリの資産に引きつけて具体的に）
- **修正案**: （コード・設定の具体的な変更。差分やファイル内容で示す）
- **修正の影響**: （使い勝手の変化。なければ「なし」）

## 問題なしと確認した項目
- （確認した観点と根拠を短く）

## 確認できなかった項目
- （理由と、ユーザーが自分で確認する方法）

## 次のステップ
修正する項目を番号で指定してください（例: 「1と3を直して」「全部直して」）。
```

**重要度の基準（このアプリ向け）**
- **重大**: APIキーが既に漏れている／漏れる状態（ソースに直書き、Git にコミット済み、公開リポジトリ）
- **高**: 他人がアプリ・APIキー・個人データに到達できる（LAN/インターネットへの公開、機密ファイルが Git 除外されていない）、任意コード実行や XSS
- **中**: 条件がそろうと情報が漏れる（LLM出力経由の外部送信、保護設定の無効化、同期フォルダでの平文保存）
- **低**: 直接の被害は小さいが整えるべき（依存バージョン未固定、アップロード上限）
- **情報**: リスクではないが知っておくべきこと（外部APIへの送信内容、未確認項目）

秘密情報は**絶対に全文を表示しない**。先頭数文字だけ残してマスクする（スキャナの出力はマスク済み）。`.env` の中身や `data/` の個人データを引用しない。存在・件数・形式だけ述べる。

### 4. 承認された項目の修正

ユーザーが番号で指定した項目だけ直す。具体的な直し方は `references/fixes.md` を参照する。

- 修正の副作用（他の端末から使えなくなる等）は、レポートで伝えたとおりかもう一度確認してから適用する。
- **APIキーが漏れていた場合**、コードを直してもキー自体は無効化されない。Google AI Studio（https://aistudio.google.com/apikey）でユーザー自身にキーを削除・再発行してもらう。Claude はキーの操作・入力をしない。
- Git 履歴の書き換え（`git filter-repo` など）や force push は、影響を説明して明示的な同意を得てから。

### 5. 再確認

修正後にスキャナを再実行し、テストがあれば実行する（このプロジェクトでは `.venv\Scripts\python -m pytest`）。直した項目が消えたこと、新しい問題が出ていないことを報告する。未対応の項目は残っていると明記する。
